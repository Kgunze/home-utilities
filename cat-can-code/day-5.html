Topic

NestJS, Strapi, PostgreSQL, DBeaver, Zod through a restaurant story.

When the system feels abstract, I can make it physical: waiter, chef, storage, warehouse, and inspector.

Today's Big Picture

Imagine we are building a restaurant system.

  • Customers come to order food.
  • The kitchen makes decisions.
  • Storage keeps ingredients.
  • Someone checks food safety.

That is exactly how the system works in tech.

The Full Restaurant Map

              ↑        ↑         ↑
            Axios    NestJS    Strapi
                         ↓
                     PostgreSQL

Who is Who

1. NestJS = The Chef

NestJS

For a 5-year-old

The chef decides how to cook and what to do if something is missing.

In real system

  • Receives request
  • Runs logic like order handling and payment
  • Calls database or Strapi
  • Sends response back

This is the main brain.

2. Strapi = The Storage Manager

Strapi

For a 5-year-old

Someone in the storage room keeps the menu, pictures, and descriptions.

In real system

  • Stores content like menu items, descriptions, and images
  • Provides APIs automatically
  • Has an admin UI so non-tech people can edit content

It is not for critical logic, only content.

3. PostgreSQL = The Warehouse

PostgreSQL

For a 5-year-old

A big warehouse storing all important things safely.

Stores

  • Customers
  • Orders
  • Payments

DBeaver

5. Zod = The Food Safety Inspector

Zod

For a 5-year-old

Someone checks if food is safe before cooking and serving.

Where Zod Works

Before cooking (request)

Waiter -> Chef
       ↑
      Zod checks

After getting ingredients (response)

Storage -> Chef
          ↑
         Zod checks

Zod protects every door.

Key Insight

Zod is used many times. NestJS decides when to use it.

Full Flow

Scenario: Customer places an order

  1. Customer opens the menu and places an order.
  2. Waiter (Axios) brings order.
  3. Zod checks order.
  4. Chef (NestJS) processes it.
  5. Chef checks Warehouse (PostgreSQL) and Storage (Strapi).
  6. Zod checks returned data again.
  7. Chef sends result.
  8. Waiter delivers to customer.

Day 5 Continuation: Chef Requests Menu Data

This is one of the most important scenes in the whole restaurant story, because it shows exactly where trust can break.

Scene Script

  • Chef (NestJS): "Storage, give me the menu."
  • Storage Manager (Strapi): "Okay, let me get it from the warehouse."
  • Warehouse (PostgreSQL): "Here is the data."
  • Storage Manager: "Here's your menu."
  • Chef: "Let me double-check before serving."

Reality Diagram

NestJS (Chef)
   -> HTTP Request
Strapi (Storage Manager)
   -> Query
PostgreSQL (Warehouse)
   <- Data
Strapi (formats response)
   <- HTTP Response
NestJS
   <- Zod validation

Codex Breakdown

1. Chef sends request

NestJS -> HTTP -> Strapi API
  • NestJS acts as the backend controller.
  • It calls a Strapi endpoint to ask for content.
  • Strapi is a headless CMS that exposes APIs automatically.

Source: Strapi architecture

2. Strapi processes request

Request -> Strapi Controller -> Service Layer
  • Strapi routes the request.
  • It applies middleware.
  • It prepares the database query.

Inside Strapi, this follows a controller, service, and database-layer style architecture.

3. Strapi queries database

Strapi -> PostgreSQL
  • PostgreSQL stores the structured content.
  • Strapi reads from it when content is requested.

Source: Strapi with PostgreSQL

4. Database returns data

PostgreSQL -> Strapi

The database returns rows and raw content values back to Strapi.

5. Strapi formats API response

Strapi -> JSON -> NestJS

Strapi turns the database result into an API response that NestJS can consume.

{
  "data": [
    { "id": 1, "name": "Fried Rice", "category": "food", "price": 120 }
  ]
}

6. Chef validates the data

Strapi Response -> Zod -> NestJS
  • Zod checks that the structure is what NestJS expects.
  • This prevents broken or surprising data from entering the system.

Codex Insight

This scene is one of the most dangerous points in the system.

Risk if validation is skipped

Strapi -> NestJS (no validation)
  • Wrong data shape
  • Missing fields
  • Silent UI crash
  • Security vulnerabilities

Correct pattern

External API -> ALWAYS validate -> THEN use

Mapping to the Existing Architecture

Frontend
   ->
BFF (validation layer)
   ->
External API

This exact scene matches the same architecture pattern:

BFF -> Strapi -> Validate -> Return

What This Scene Teaches

  • Strapi is the API and content layer.
  • PostgreSQL is the data storage layer.
  • NestJS is the controller and decision maker.
  • Zod is trust-boundary protection.
The chef never trusts the storage blindly. Every ingredient must be checked before cooking.

Concrete Boundary Example: Strapi to NestJS

This is the best place for a real Zod example, because it sits exactly where the risky boundary appears in the story.

First I saw the scene. Now I can see the code that protects the scene.

Scenario: Strapi Returns Menu Data

What comes from Strapi is still untrusted until NestJS validates it.

{
  "data": [
    {
      "id": 1,
      "name": "Fried Rice",
      "category": "food",
      "price": "1000"
    }
  ]
}

This is dangerous if the system trusts it blindly, because price is a string instead of a number.

Step 1 - Define Zod Schema

The inspector needs a rule book before it can check anything.

import { z } from "zod";

export const DishSchema = z.object({
  id: z.number(),
  name: z.string(),
  category: z.enum(["food", "drink"]),
  price: z.number(),
});

export const MenuResponseSchema = z.object({
  data: z.array(DishSchema),
});

Step 2 - Validate Strapi Response

NestJS should validate the API response before business logic touches it.

const response = await fetch("https://strapi/api/menu-items");
const json = await response.json();

const parsed = MenuResponseSchema.safeParse(json);

if (!parsed.success) {
  throw new Error("Invalid data from Strapi");
}

return parsed.data;

What Happens Here

Because "price": "1000" is a string, Zod fails the check.

Expected number, received string

The system stops here, which is exactly what safe architecture should do.

Fix Option: Safe Coercion

If the external system is messy but predictable, the schema can convert carefully.

export const DishSchema = z.object({
  id: z.number(),
  name: z.string(),
  category: z.enum(["food", "drink"]),
  price: z.coerce.number(),
});

Another Real Case: Missing Field

Sometimes the shape is incomplete instead of just the wrong type.

{
  "data": [
    {
      "id": 1,
      "price": 120
    }
  ]
}

Zod will reject it because the required name and category fields are missing.

Required field "name" is missing
Required field "category" is missing

Advanced Pattern: Strict Mode

Strict mode is a good fit here because it hardens the boundary against unexpected fields.

export const DishSchema = z.object({
  id: z.number(),
  name: z.string(),
  category: z.enum(["food", "drink"]),
  price: z.number(),
}).strict();

If Strapi sends extra data that NestJS did not ask for, validation fails instead of silently passing it through.

{
  "id": 1,
  "name": "Fried Rice",
  "category": "food",
  "price": 1000,
  "hack": "malicious"
}

Transform Data Safely

Validation can also prepare trusted data for the next layer.

export const DishSchema = z.object({
  id: z.number(),
  name: z.string(),
  category: z.enum(["food", "drink"]),
  price: z.number(),
}).transform((data) => ({
  ...data,
  displayPrice: `${data.price} THB`
}));

Full Integration in NestJS

This is the chef applying the inspection step before serving anything to the rest of the kitchen.

async getMenu() {
  const res = await fetch("https://strapi/api/menu-items");
  const json = await res.json();

  const parsed = MenuResponseSchema.safeParse(json);

  if (!parsed.success) {
    console.error(parsed.error);
    throw new Error("Strapi response invalid");
  }

  return parsed.data;
}

Real Production Insight

Without validation, bad data can travel quietly until it explodes somewhere deeper.

const dishes = json.data;
dishes[0].price.toFixed(2);

If price is a string, that becomes a runtime crash.

With Zod, the system blocks the bad data before it reaches business logic.

Rule to Remember

If data comes from outside the system, validate with Zod before using it.
Strapi = untrusted
Zod = gatekeeper
NestJS = decision maker

The Other Door: Customer Order Validation

The menu scene protects the response boundary. The order scene protects the request boundary.

The waiter should not send a broken order into the kitchen.

Scene: Customer Places Order

Now the data moves in the other direction.

Customer -> Waiter -> Chef
          request
            ↑
           Zod checks

Order Schema

const OrderSchema = z.object({
  customerId: z.string(),
  items: z.array(
    z.object({
      dishId: z.number(),
      quantity: z.number().min(1),
    })
  ).min(1),
});

Happy Path

{
  "customerId": "cust_123",
  "items": [
    { "dishId": 1, "quantity": 2 }
  ]
}

Zod accepts this, so NestJS can continue to pricing, stock checks, and payment.

Invalid Request Example

{
  "customerId": "cust_123",
  "items": [
    { "dishId": "1", "quantity": 0 }
  ]
}

This fails because dishId has the wrong type and quantity is too small.

Expected number, received string
Number must be greater than or equal to 1

NestJS Style Request Validation

async createOrder(payload: unknown) {
  const parsed = OrderSchema.safeParse(payload);

  if (!parsed.success) {
    console.error(parsed.error);
    throw new Error("Invalid order request");
  }

  return this.orderService.create(parsed.data);
}

Payment Schema

Once the order is valid, the bill can also have its own rule book.

const PaymentSchema = z.object({
  orderId: z.string(),
  totalAmount: z.number(),
  method: z.enum(["cash", "card"]),
});

Important Rules You Learned Today

Don't mix roles

  • Strapi ≠ main database
  • PostgreSQL ≠ API provider
  • NestJS ≠ validator

Correct Responsibilities

Tool Responsibility
NestJS Logic and control
Strapi Content
PostgreSQL Core data
Zod Validation
DBeaver Debug and view

Security Thinking

  • Never trust incoming request, use Zod.
  • Never trust external API, validate again.
  • Never expose database directly.
  • Never store sensitive data in Strapi.

Final Understanding

The chef (NestJS) runs the kitchen. The warehouse (PostgreSQL) keeps important stuff. The storage manager (Strapi) keeps menus and pictures. The inspector (Zod) checks everything is safe. The window (DBeaver) lets you see inside.

One Sentence to Remember

NestJS controls the system, PostgreSQL stores truth, Strapi manages content, Zod protects everything.
