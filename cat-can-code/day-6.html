Topic

Async Flow with Axios + Promise + await + Try Catch + Retry + Timeout + Fallback through a restaurant timeline.

In a real system, things do not happen instantly. Orders take time, data takes time, and network calls take time.

Today's Big Idea

That is why these three ideas matter together.

  • Promise means the result will be ready later.
  • await means this async function waits for the result before continuing.
  • Axios is the tool that sends the request across the network.

Inside NestJS

The chef does not guess. The chef waits for each important step to finish in order.

async createOrder(input) {
  OrderSchema.parse(input);

  const menu = await axios.get("https://strapi/api/menu");

  MenuSchema.parse(menu.data);

  await prisma.order.create({
    data: input,
  });

  return { success: true };
}
await keeps the order correct: get data first, validate it next, save only after that.

Unhappy Case

Sometimes the dish is not available, so the order flow must stop safely and let the customer choose again.

1. Customer orders dish
2. Chef checks storage
3. Dish is not available
4. Chef cancels order
5. Customer re-orders a new dish
6. System retries flow
7. Success
async createOrder(input) {
  OrderSchema.parse(input);

  try {
    const menu = await axios.get("https://strapi/api/menu");

    const parsed = MenuSchema.safeParse(menu.data);

    if (!parsed.success) {
      throw new Error("Invalid menu data");
    }

    const dish = parsed.data.find((d) => d.id === input.dishId);

    if (!dish) {
      throw new Error("Dish not available");
    }

    await prisma.order.create({ data: input });

    return { success: true };
  } catch (error) {
    return {
      success: false,
      message: "Dish unavailable, please reorder",
    };
  }
}

Missing await Bug

Without await, the code tries to use data before the network request has finished.

const menu = axios.get("https://strapi/api/menu");
console.log(menu.data);

That is like the chef cooking before ingredients arrive.

  • The request has started.
  • The result is still a Promise.
  • menu.data is not ready yet.

Try Catch in the Restaurant

Async flow explains how work takes time. try/catch explains what the system does when that work fails.

In the restaurant story, the manager steps in when something unexpected goes wrong.

Concept Restaurant Role
try Let's try to serve the dish.
catch Something failed, so handle the situation safely.
throw The kitchen reports that something went wrong.

Happy Case

No error happens, so the manager does not need to step in.

async function orderFood() {
  try {
    const dish = await kitchenCook("pasta");
    console.log("Serve:", dish);
  } catch (error) {
    console.log("Sorry, something went wrong");
  }
}
If everything works, catch stays silent.

Unhappy Case

When the kitchen cannot cook the order, it throws an error and the manager takes control.

async function orderFood() {
  try {
    const dish = await kitchenCook("steak");
    console.log("Serve:", dish);
  } catch (error) {
    console.log("Dish unavailable, suggest chicken instead");
  }
}
async function kitchenCook(food: string) {
  if (food === "steak") {
    throw new Error("Out of ingredients");
  }

  return "Delicious " + food;
}

Architecture Meaning

This fits your BFF layer exactly: backend or validation code can throw, and the boundary layer catches errors so the UI gets a safe experience.

try {
  const response = await BffHttpInstance.post(...);

  const validation = schema.safeParse(response);

  if (!validation.success) {
    throw new SchemaValidationError(...);
  }

  return validation.data;
} catch (error) {
  logError(error);
  return { success: false, message: "Please try again" };
}

Why This Matters

  • Without try/catch, a failed async call can break the flow and crash the experience.
  • With try/catch, the system can log the real problem and show a safe message to the user.
  • try/catch does not magically fix the error. It controls what happens next.

Retry, Timeout, and Fallback

Real systems must handle more than simple success or failure. They also need a plan for slow responses, flaky services, and repeated problems.

Concept Restaurant Meaning
Retry Ask the kitchen to try cooking again.
Timeout Stop waiting if the kitchen takes too long.
Fallback Offer another dish instead of leaving the customer with nothing.

Case 1: Kitchen Is Slow

Sometimes the kitchen does not fail. It is just too slow, and the manager decides the customer should not wait forever.

async function orderFood() {
  try {
    const dish = await withTimeout(kitchenCook("steak"), 3000);
    console.log("Serve:", dish);
  } catch (error) {
    console.log("Sorry, kitchen is too slow. Please choose another dish.");
  }
}
function withTimeout(promise: Promise<any>, ms: number) {
  return Promise.race([
    promise,
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error("Timeout")), ms)
    ),
  ]);
}
Timeout protects user experience by refusing to wait forever.

Case 2: Kitchen Failed, So Try Again

If the first cooking attempt fails, a controlled retry can recover without bothering the customer.

async function retryCook(food: string, retries = 2) {
  for (let i = 0; i <= retries; i++) {
    try {
      return await kitchenCook(food);
    } catch (error) {
      if (i === retries) throw error;
      console.log("Retry cooking...");
    }
  }
}

Case 3: Still Fails, So Use a Fallback

If retries still do not work, the system should still have a safe plan B.

async function orderWithFallback() {
  try {
    const dish = await retryCook("steak");
    return dish;
  } catch {
    return "chicken";
  }
}
Fallback means the customer still gets a result, even if it is not the first choice.

@Controller("orders")
export class OrderController {
  constructor(private readonly orderService: OrderService) {}

  @Get()
  async orderFood() {
    return this.orderService.handleOrder("steak");
  }
}
@Injectable()
export class OrderService {
  constructor(private kitchen: KitchenService) {}

  async handleOrder(food: string) {
    try {
      const result = await this.retry(() =>
        this.withTimeout(() => this.kitchen.cook(food), 3000)
      );

      return result;
    } catch {
      return "chicken";
    }
  }

  async retry(fn: () => Promise<any>, retries = 2) {
    for (let i = 0; i <= retries; i++) {
      try {
        return await fn();
      } catch (e) {
        if (i === retries) throw e;
      }
    }
  }

  async withTimeout(fn: () => Promise<any>, ms: number) {
    return Promise.race([
      fn(),
      new Promise((_, reject) =>
        setTimeout(() => reject(new Error("Timeout")), ms)
      ),
    ]);
  }
}
@Injectable()
export class KitchenService {
  async cook(food: string) {
    if (food === "steak") {
      throw new Error("Out of ingredients");
    }

    return "Delicious " + food;
  }
}

Production Insight

  • Always await external calls when later logic depends on their result.
  • Always validate responses with Zod before trusting them.
  • Always handle failure with try/catch or a clear error strategy.
  • Limit retry attempts so recovery does not become internal overload.
  • Always use timeout around risky calls to avoid infinite waiting.
  • Use fallback when the user still needs a safe outcome.
  • Keep internal error detail in logs and return friendly messages to users.

Final Summary

The system is not instant, and it is not perfect. Axios sends, Promise represents work in progress, await keeps the order safe, try/catch controls failure, retry gives recovery another chance, timeout protects responsiveness, fallback protects user experience, Zod protects the data, and NestJS decides what happens next.

One Sentence to Remember

await controls timing, try/catch handles failure, retry tries again, timeout stops endless waiting, and fallback makes sure the user is never abandoned.
