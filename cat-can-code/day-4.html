Day 4 - Standard Next.js Project with Zod and Axios

Today I stopped seeing Next.js as just pages and started seeing a production flow: UI to BFF to validation to backend and back again.

Cat Can Code April 7, 2026 7 min read

Big Idea

I can explain today's lesson with a very simple game rule.

You choose a building.

If the building is a hotel, then it must have stars.

The stars must be between 0 and 5. Other building types can treat stars as optional.

What code is really doing here is turning game rules into data rules.

The Rule Book

Zod feels like a rule-checker robot that reads the rule book before data is allowed through.

import { z } from "zod";

export const PropertySchema = z.discriminatedUnion("propertyType", [
  z.object({
    propertyType: z.literal("HOTEL"),
    ratingStar: z.number().min(0).max(5),
  }),
  z.object({
    propertyType: z.literal("VILLA"),
    ratingStar: z.number().min(0).max(5).optional(),
  }),
]);

If I say hotel without stars, the robot blocks me. If I give 10 stars, it blocks me again. If I give a valid value like 3, it lets the data pass.

How the Whole System Works

User -> UI -> Zod (rules) -> BFF -> Backend

This still matches the bigger architecture I've been learning.

The user interacts with the UI, Zod checks the rules, the BFF acts like the gatekeeper, and the backend does the real work.

If the order is wrong, the system should stop early instead of letting bad data travel deeper.

New Insight: Zod Error Codes to UI State to i18n

I can now see another important layer in the system.

Zod does not talk to users. It talks to the system using codes. The UI translates those codes into human language and visible states.
User input
  -> Zod validation (returns code)
  -> UI state management
  -> i18n mapping
  -> User sees message

Zod as a Code Generator

Old thinking is to hardcode human text directly inside validation.

z.string().email({ message: "Invalid email address" })

That works at first, but it does not scale well.

New thinking is to let Zod return a stable system code instead.

z.string().email({ message: "INVALID_EMAIL" })
{
  path: ["email"],
  message: "INVALID_EMAIL"
}

That means Zod is defining what is wrong, not trying to act like the final copywriter for the product.

The Missing Bridge: UI State

Zod tells me what failed, but the UI still decides where the error appears, when it appears, and how the screen should react.

type FormState = {
  errors: Record<string, string>;
  status: "idle" | "error" | "success" | "loading";
};
if (!result.success) {
  setState({
    status: "error",
    errors: result.error.flatten().fieldErrors,
  });
  return;
}

setState({ status: "success" });

This is the bridge between machine validation and product behavior.

i18n Mapping Layer

Once the UI has the code, the app can translate that code into whatever language the user needs.

const errorMap = {
  "en-US": {
    INVALID_EMAIL: "Please enter a valid email address",
    REQUIRED: "This field is required",
  },
  "vi-VN": {
    INVALID_EMAIL: "Vui lòng nhập email hợp lệ",
    REQUIRED: "Trường này là bắt buộc",
  },
};
<p>{errorMap[locale][errorCode]}</p>

This makes the system much more scalable than scattering random strings across components.

Success Codes Matter Too

I should not think only about errors. Success is also a system state that benefits from standard codes.

const successMap = {
  "en-US": {
    REGISTRATION_SUCCESS: "Registration submitted successfully",
  },
  "vi-VN": {
    REGISTRATION_SUCCESS: "Đăng ký thành công",
  },
};
setState({
  status: "success",
  message: "REGISTRATION_SUCCESS",
});

That keeps success handling as consistent and localizable as error handling.

Separation of Responsibility

Layer Responsibility
Zod Define rules and return machine-friendly codes.
UI state Control behavior such as error, loading, and success.
i18n Translate codes into human language.
Backend Process valid data after it passes the boundary.

Security and Consistency Insight

This architecture improves consistency because the same code can map to the same message everywhere.

It improves localization because new languages can be added without changing validation logic.

It improves safety because random hardcoded strings are not scattered through the codebase.

z.string().email({
  message: "Email không hợp lệ",
});

That kind of hardcoded mixed-language validation is the anti-pattern I want to avoid.

Product-Level Upgrade

This makes me realize I am not just building validation anymore.

I am defining a language system between machine and human.

Machine language
INVALID_EMAIL
REQUIRED
OUT_OF_RANGE
Human language
Please enter a valid email
Vui lòng nhập email hợp lệ

Insight to Keep

Zod defines what is wrong, UI defines how to communicate it, and i18n makes sure everyone understands it.

The shortest version is even simpler:

Zod speaks in codes, UI translates, users understand.

Example: Burger with Beef or Pork

This burger story makes the whole idea much easier to hold in my head.

In the restaurant, I can order a burger, but I must choose beef or pork.

I cannot choose both, and I cannot choose nothing.

These are the rules, and Zod is the system that enforces them before the kitchen ever starts cooking.

Wrong Order: Both Meats

If I say, "I want a burger with beef and pork," the rule checker stops me.

But it does not speak to me in a polished product sentence. It returns a code.

INVALID_MEAT_SELECTION

Then the UI acts like the waiter and translates that code for the person using the app.

English
Please choose either Beef or Pork, not both.

Korean
소고기 또는 돼지고기 중 하나만 선택해주세요.

Wrong Order: No Meat

If I ask for a burger with nothing selected, that is a different rule failure.

MEAT_REQUIRED

The UI can render different language versions of the same machine code.

English
Please choose at least one meat.

Korean
고기를 하나 이상 선택해주세요.

Same system code, different human message.

Correct Order

If I choose beef only, the order is valid.

Zod says the data is okay, the kitchen can cook, and the UI can show a success state.

OK
English
Your burger is ready!

Korean
버거가 준비되었습니다!

This is a nice reminder that success is also part of the communication system, not just error handling.

What the Code Looks Like

The rules can be expressed directly in the schema.

const BurgerSchema = z
  .object({
    meat: z.array(z.enum(["BEEF", "PORK"])),
  })
  .refine((data) => data.meat.length > 0, {
    message: "MEAT_REQUIRED",
  })
  .refine((data) => data.meat.length === 1, {
    message: "INVALID_MEAT_SELECTION",
  });

And the translation dictionary can stay separate from validation.

const messages = {
  "en-US": {
    MEAT_REQUIRED: "Please choose at least one meat.",
    INVALID_MEAT_SELECTION: "Please choose either Beef or Pork, not both.",
  },
  "ko-KR": {
    MEAT_REQUIRED: "고기를 하나 이상 선택해주세요.",
    INVALID_MEAT_SELECTION: "소고기 또는 돼지고기 중 하나만 선택해주세요.",
  },
};

What This Example Teaches

You order burger
  -> Zod checks rules and returns code
  -> UI translates the code
  -> Kitchen only receives valid orders

Without this system, the kitchen gets confusing orders and the user gets confusing behavior.

With this system, the rules are clear, the communication is understandable, and the whole flow works in any language.

You can pick beef or pork, but not both, and the waiter explains it in your language.

Why Not Use if and else Everywhere

At first it feels like I could just write conditional checks by hand.

if (propertyType === "HOTEL") {
  if (!ratingStar) throw Error("Required");
}

But that creates several problems.

  • The same logic gets scattered across UI code, API code, and validation code.
  • TypeScript still does not fully trust the data shape after a casual check.
  • Small changes like "hotel" instead of "HOTEL" can break the logic silently.
  • Bad backend data can still sneak through and break the UI later.
if (propertyType === "HOTEL") {
  ratingStar // still maybe undefined
}

Why Zod Discriminated Union Is Better

The important shift is that the rule lives in one place instead of being repeated everywhere.

z.discriminatedUnion(...)
What it gives me Why it matters
Single source of truth The rule only needs to exist once.
Auto type safety When the type is HOTEL, ratingStar is guaranteed.
Impossible states blocked HOTEL without rating and rating above 5 are rejected early.
Cleaner thinking I stop thinking in scattered conditionals and start thinking in valid structures. 
if (data.propertyType === "HOTEL") {
  data.ratingStar // guaranteed exists
}

The Upgrade in My Brain

Before, I thought the job was to check things with if and else after the fact.

Now I see the better approach:

Design the rules so invalid data cannot exist in the first place.

That is a much deeper mindset shift than just learning a new library.

Day 4 Final Insight

Don't check data after it breaks. Design it so it can't break.

This feels like the real lesson behind Zod, BFF, and strong project structure.
