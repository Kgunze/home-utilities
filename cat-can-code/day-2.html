Day 2 — From Routes to Systems (Thinking in NestJS)

Starting to understand backend… properly. Not as “API endpoints”. But as a system of responsibility layers.

Cat Can Code April 5, 2026 5 min read

Starting to understand backend… properly.

Not as “API endpoints”.

But as a system of responsibility layers.

Recap from Learning

Today’s focus was NestJS — a backend framework that forces structure.

At first, it feels heavier than Express.

But then I realized:

It’s not heavier. It’s clearer.

What NestJS Really Is

  • Controller → handles incoming requests
  • Service → contains business logic
  • Module → organizes everything

This creates a system where:

Each part has a job. Nothing overlaps.

The Flow (Interactive)

Hover each block to understand what it does. Think of it as how a request travels inside the system.

Request User sends a request from UI →
Controller Receives request and routes it →
Service Handles business logic →
Database Stores and retrieves data →
Response Returns result to user

Click a block to expand the note.

Prerequisites (Reality Check)

Before jumping into NestJS, I see why these matter:

  • JavaScript → core language understanding
  • TypeScript → structure and type safety
  • Node.js → runtime environment
  • Express → baseline backend thinking

NestJS is not replacing these.

It’s organizing them.

Insight

If Express is:

“Freedom to build anything”

NestJS is:

“Structure to scale safely”

🧩 Key Concepts (Translated Simply)

Controller = Door

  • Receives requests
  • Decides where to send them

Example thinking:

“User wants workout plan → send to service”

Service = Brain

  • Handles logic
  • Processes data
  • Talks to database

Example:

“Given user data → generate structured plan input”

Module = Organizer

  • Groups related logic together
  • Keeps system scalable

Example:

“AuthModule, UserModule, WorkoutModule”

⚙️ Dependency Injection (Important Shift)

Instead of manually connecting things, NestJS injects dependencies automatically.

Meaning:

“You don’t build connections every time — the system wires it for you.”

Why this matters:

  • Less coupling
  • Easier testing
  • Cleaner scaling

🧠 Mental Upgrade

Before:

“Call API → get data”

Now:

“Route request through controlled layers”

🔍 Backend Is Not Just Data

I used to think backend = database operations. But actually it is:

  • Validation layer
  • Logic layer
  • Security layer
  • Structure layer

Database is just one part.

⚠️ Hidden Complexity (Again)

Things that look simple:

  • Routing → actually access control problem
  • Services → can become messy without boundaries
  • Modules → require good domain thinking

🛡️ Security Awareness (Day 2 Note)

  • Never trust incoming data
  • Always validate DTOs
  • Separate public vs protected endpoints
  • Avoid leaking internal errors to client
  • Keep environment variables strictly server-side

Day 2:

“Understood how backend is structured inside that system”

Small Reflection

Today I learned:

Good backend is not about writing logic.

It’s about:

  • Designing responsibility
  • Enforcing boundaries
  • Making systems predictable
