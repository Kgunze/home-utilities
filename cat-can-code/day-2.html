Day 2 — From Routes to Systems (Thinking in NestJS)

Starting to understand backend… properly. Not as “API endpoints”. But as a system of responsibility layers.

Cat Can Code April 5, 2026 5 min read

Starting to understand backend… properly.

Not as “API endpoints”.

But as a system of responsibility layers.

Recap from Learning

Today’s focus was NestJS — a backend framework that forces structure.

At first, it feels heavier than Express.

But then I realized:

It’s not heavier. It’s clearer.

What NestJS Really Is

  • Controller → handles incoming requests
  • Service → contains business logic
  • Module → organizes everything

This creates a system where:

Each part has a job. Nothing overlaps.

The Flow (Interactive)

Hover each block to understand what it does. Think of it as how a request travels inside the system.

Request User sends a request from UI →
Controller Receives request and routes it →
Service Handles business logic →
Database Stores and retrieves data →
Response Returns result to user

Click a block to expand the note.

Prerequisites (Reality Check)

Before jumping into NestJS, I see why these matter:

  • JavaScript → core language understanding
  • TypeScript → structure and type safety
  • Node.js → runtime environment
  • Express → baseline backend thinking

NestJS is not replacing these.

It’s organizing them.

Insight

If Express is:

“Freedom to build anything”

NestJS is:

“Structure to scale safely”

All three pieces work together at the same time when a request flows through the system.

🚪
✏️ arrow entering a box labeled controller

Controller = Door

Business Thinking

Receives user intent and routes it correctly.

Example: User clicks “Generate Workout Plan”.

Code Logic
@Post('/workout')
createWorkout(@Body() data) {
  return this.workoutService.generate(data);
}
Controller should stay thin — no heavy logic here.
🧠
✏️ brain with arrows branching out

Service = Brain

Business Thinking

Processes logic and makes decisions.

Example: Interpret user fitness data and create plan input.

Code Logic
generate(data) {
  const structured = this.transform(data);
  return structured;
}
This is where your real system intelligence lives.
📦
✏️ boxes grouped together

Module = Organizer

Business Thinking

Groups related logic into domains.

Example: WorkoutModule handles everything about workouts.

Code Logic
@Module({
  controllers: [WorkoutController],
  providers: [WorkoutService],
})
Prevents chaos as system grows.

⚙️ Dependency Injection (Important Shift)

Instead of manually connecting things, NestJS injects dependencies automatically.

Meaning:

“You don’t build connections every time — the system wires it for you.”

Why this matters:

  • Less coupling
  • Easier testing
  • Cleaner scaling

🧠 Mental Upgrade

Before:

“Call API → get data”

Now:

“Route request through controlled layers”

Function Arguments = System Clarity

Today I hit a line from Clean Code that looks simple, but changes how I see everything:

The ideal number of arguments for a function is zero → one → two. Avoid more than that.

At first, it feels like a coding style rule.
But it’s not.
It’s a system design rule.

🧩 Where This Appears in My System

From yesterday’s flow:

Request → Controller → Service → Database → Response

Now zoom into this part:

Controller → Service

This is where function arguments live.

❌ The Wrong Way (Feels normal, but dangerous)

generateWorkoutPlan(goal, experience, daysPerWeek, equipment, injuries)

Looks fine. But actually:

  • Hard to read
  • Easy to mix up order
  • Hard to scale
  • Hard to validate
  • Hard to secure

This is called a code smell — too many parameters usually means poor structure (Wikipedia)

✅ The Better Way (System Thinking)

generateWorkoutPlan(userProfile)

Where:

const userProfile = {
  goal: "lose weight",
  experience: "beginner",
  daysPerWeek: 3,
  equipment: ["dumbbells"],
  injuries: []
}

Now:
One argument = one meaning.

🧠 What Changed (Important Insight)

Before:
“Function receives values”

Now:
“Function receives a structured concept”

🏗️ Mapping to NestJS (This clicked for me)

Controller

@Post('/plan')
generate(@Body() dto: CreatePlanDto) {
  return this.service.generate(dto)
}

Service

generate(profile: CreatePlanDto) {
  return this.buildPlan(profile)
}

🔍 Why This Rule Exists (Deeper Truth)

Functions with many arguments:

  • Break readability
  • Increase testing complexity (Medium)
  • Hide real responsibility

Which usually means:
“The function is doing too many things”.

⚠️ Hidden Risk (System + Security)

  • Wrong data mapping (silent bugs)
  • Missing validation points
  • Injection risks if fields are loosely handled
  • Tight coupling between layers

🧠 Mental Model Upgrade

Function is not just:
“something that runs logic”

Function is:
“A boundary of responsibility”

And arguments define:
“What is allowed to cross that boundary”

🔍 Backend Is Not Just Data

I used to think backend = database operations. But actually it is:

  • Validation layer
  • Logic layer
  • Security layer
  • Structure layer

Database is just one part.

⚠️ Hidden Complexity (Again)

Things that look simple:

  • Routing → actually access control problem
  • Services → can become messy without boundaries
  • Modules → require good domain thinking

🛡️ Security Awareness (Day 2 Note)

  • Never trust incoming data
  • Always validate DTOs
  • Separate public vs protected endpoints
  • Avoid leaking internal errors to client
  • Keep environment variables strictly server-side
