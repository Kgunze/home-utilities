Day 3 - Rebase, Conflict Thinking & Production Safety

Today I stopped thinking of Git as commands and started seeing it as production risk control.

Cat Can Code April 6, 2026 7 min read

Today was the first time I stopped thinking of Git as commands and started seeing it as a simulation engine for production risk.

The Cursor prompt is not just automation. It is enforcing a discipline:

Solve problems before they reach staging or production.

The Mental Shift

Before today, git rebase felt like just another Git operation.

Now it feels like a replay system for reality.

Rebase asks: if production already changed, would my feature still work?

That changes the whole mindset. I am no longer building on assumptions. I am rebuilding on current truth.

Rebase as Local Simulation

This flow looks simple:

feature branch
  -> rebase onto staging
  -> resolve conflicts
  -> validate build
  -> open PR

But it is not just a workflow. It is a safety pipeline.

Rebase = rebuild changes as if the base branch was always correct.

Conflict Resolution = Engineering Judgment

A conflict is not really asking, "Which code do I pick?"

It is asking, "Two versions of reality exist. How do I reconcile them without breaking the system?"

<<<<<<< HEAD (staging)
new API schema
=======
my feature logic
>>>>>>> feature

The important questions are:

Question Why it matters
Did the API change? Prevents breaking frontend and backend coordination.
Is my feature outdated? Stops silent bugs from shipping.
What depends on this? Avoids cascading failures across layers.

Correct Strategy

  • Keep the latest contract from staging.
  • Adapt feature logic to that contract.
  • Never blindly overwrite one side with the other.

This is what backward compatibility and system integrity look like in real work.

Validation Is the Truth Check

These commands used to feel like routine steps:

pnpm install
pnpm build
pnpm test

Now they feel like system verification after surgery.

Rebase can create hidden type mismatches, broken imports, or invalid API contracts. Build and test are where the system tells the truth.

After conflict resolution, validation is the first line of defense.

Commit Hygiene Is Also Security

Small cleanup steps are not cosmetic.

  • Remove console.log debugging.
  • Remove temporary testing logic.
  • Check how environment variables are being used.

If I skip this, debug behavior or sensitive information can reach production by accident.

Why Force Push Is Allowed and Dangerous

git push --force-with-lease

Today I learned why this can be acceptable after a rebase and why it still demands caution.

  • It is safer when I rebased locally and validated the result.
  • It is dangerous because it rewrites history.
  • It becomes reckless if I do not control the branch lifecycle.
Force push is safe only when you understand exactly whose history you are rewriting.

The Architecture Connection

This clicked when I mapped it back to the real stack:

  • Frontend depends on the BFF.
  • BFF enforces schema through validation.
  • Backend defines the contract.

Without this workflow:

Layer Risk
Frontend Calls an outdated API.
BFF Schema no longer matches.
Backend Rejects the request or behaves unexpectedly.
User Sees the failure even though the branch looked fine locally.

This is what the workflow is protecting: contract consistency, type safety, and stable release flow.

Security Thinking That Quietly Emerged

  • Silent contract drift is dangerous because old frontend assumptions can survive longer than expected.
  • Hidden breaking changes often pass local intuition but fail in staging or production.
  • Unsafe merge behavior delays conflict discovery until the most expensive moment.

This makes the workflow feel much closer to DevSecOps than simple Git hygiene.

New Knowledge: BFF (Backend for Frontend)

BFF means a backend layer designed specifically for a frontend.

Frontend (NextJS)
  -> BFF Layer
  -> Backend (NestJS / Services)

Instead of the frontend calling backend services directly, the frontend talks to a BFF that adapts, filters, and stabilizes the interaction.

BFF is a controlled translation layer that protects, adapts, and stabilizes communication between frontend and backend.

Where BFF Came From

The BFF pattern emerged in the early 2010s during the rise of microservices, especially when teams had to support web, mobile, and tablet clients from the same backend ecosystem.

The problem was simple: every client needed different data shapes and different performance tradeoffs, but one shared backend kept becoming bloated and difficult to maintain.

Without BFF
Mobile -> Backend (too heavy)
Web -> Backend (missing fields)

With BFF
Web -> Web-BFF -> Backend
Mobile -> Mobile-BFF -> Backend

That is why the pattern matters. Each frontend gets exactly what it needs without forcing the core backend to become a dumping ground for presentation concerns.

How BFF Works in This Architecture

NextJS (FE)
  -> packages/bff
  -> NestJS Backend

This layer is powerful because it creates a stable contract for the frontend, even when backend services evolve underneath it.

The BFF responsibilities are practical:

  • Aggregate multiple backend calls into one frontend-friendly response.
  • Transform backend field names and shapes into cleaner UI contracts.
  • Validate responses with Zod before invalid data reaches the frontend.
  • Normalize errors and hide internal backend details.
  • Act as a security boundary for tokens, endpoints, and sensitive data.
const user = await getUser()
const bookings = await getBookings()

return { user, bookings }
schema.safeParse(response)

Why BFF Matters So Much

Without a BFF, the frontend is tightly coupled to backend contracts.

With a BFF, the frontend depends on a stable BFF contract while the BFF absorbs backend changes and translations.

This directly reduces the frontend-backend conflict surface that shows up during rebase and integration.

That is why this connects so strongly to today's rebase lesson. A good BFF does not remove all risk, but it moves risk into a controlled layer.

How BFF Can Be Misused

BFF becomes dangerous when it stops acting like an adapter and starts pretending to own business truth.

  • Putting discount rules, balance logic, or domain decisions into the BFF is the wrong boundary.
  • Duplicating backend rules in the BFF creates inconsistency.
  • Skipping validation means trusting backend responses blindly and inviting runtime failures.
if (user.balance > 1000) {
  applyDiscount()
}

Logic like that belongs in the real backend domain layer, not in the frontend adapter layer.

Security Perspective

The BFF is also a security boundary, not just a convenience layer.

  • It reduces direct backend exposure to the public client.
  • It can prevent over-fetching of sensitive fields.
  • It can keep token handling on the server side instead of leaking responsibility to the client.
Backend returns
{
  "user": "...",
  "passwordHash": "...",
  "internalRole": "admin"
}

BFF returns
{
  "user": "..."
}

My New Mental Model for BFF

Before, I thought API mostly meant backend responsibility.

Now I see API as an experience layer tailored for the frontend.

The rules are becoming clear:

  • BFF is an adapter, not the owner of business truth.
  • Always validate.
  • Keep frontend dependent on stable BFF contracts, not volatile backend responses.
  • Optimize the contract for the client that actually consumes it.
Concept Connection
Rebase Resolves frontend to BFF integration drift earlier.
NextJS API Can act as a BFF layer.
Zod validation Enforces the BFF contract before data reaches UI.
DevSecOps Makes BFF a practical security boundary, not just a coding pattern.

This feels like architecture-level thinking, not just coding syntax.

New Knowledge: Zod Explained Like I'm 5

I imagine a cookie shop.

Kids come in and try to order cookies.

The rule is simple: every order must say the flavor and the quantity.

Order must have
- flavor (chocolate or vanilla)
- quantity (a number)

In this story, Zod is the friendly guard at the door checking every order before it goes inside.

How the Guard Works

A good order sounds like this:

I want 2 chocolate cookies

A bad order sounds like this:

I want blue cookies
I want many cookies

Zod listens and decides:

  • If the order is real, it says, "Okay, come in."
  • If the order is wrong, it says, "Nope, that is not a real order."
Zod checks whether the shape of the data matches the rules we promised to accept.

The Kitchen Problem

Then the kitchen, which is like the backend, makes the cookies and sends something back.

Usually it should send cookies.

Here are your cookies 🍪🍪

But if the kitchen makes a mistake, it might send something unexpected.

Here are your... broccoli

Without validation, the kid just receives nonsense and cries.

With Zod checking the response too, the guard stops it and says, "Wait, this is not cookies."

The Full Zod Story

Kid -> Zod checks -> Kitchen -> Zod checks -> Kid gets cookies

That means Zod is useful in two directions:

  • It checks requests before bad input enters the system.
  • It checks responses before bad output reaches the frontend.
Real system Kid story
API request Kid order
Backend Kitchen
Zod Guard
Data validation Checking the order
Error handling Saying "Nope"

Why This Matters in Real Apps

Without Zod, wrong data can travel through the app and break things later.

With Zod, bad data is rejected early while the problem is still small and understandable.

  • Wrong request data gets blocked before it reaches business logic.
  • Wrong response data gets blocked before it breaks the UI.
  • Users get safer behavior and clearer failures instead of confusing crashes.
schema.safeParse(response)
Zod makes sure what goes in and what comes out is exactly what we expect.

My Zod Mental Model

Zod is a guard that makes sure kids only ask for real cookies and the kitchen only gives back real cookies.

Translated back into software, that means data going in and out of the system is checked before trust is given.

That is why Zod fits perfectly with the BFF layer and today's rebase lesson: it helps catch contract drift before the frontend quietly breaks.

New Insight: Axios and How Data Travels

Axios is the messenger that sends data between my app and the server.

It does not validate data. That is Zod's job.

It does not decide business logic. That belongs to the backend.

Axios moves data. Zod decides whether that data is safe to trust.
Frontend (NextJS UI)
  -> Zod checks input
  -> Axios sends request
  -> BFF / API
  -> Backend (NestJS)
  -> Axios receives response
  -> Zod checks response

Where Axios Fits in a Real Flow

In the Google Login example, the user clicks "Continue with Google."

Then Axios sends the request:

await axios.post('/api/auth/google', {
  token: googleToken
})

The backend responds with something like this:

{
  "accessToken": "abc123",
  "user": { "name": "Kyle" }
}

Axios brings that response back through res.data. It delivers the package, but it does not inspect whether the package is correct.

const res = await axios.post(...)
const data = res.data

That is the critical insight: Axios is transport, not trust.

Kid Version: Delivery Person and Cookies

If the cookie story continues, Axios is the delivery person.

You say, "I want chocolate cookies," and Axios carries the order to the kitchen and brings something back.

Sometimes the kitchen gives cookies. Sometimes it accidentally sends broccoli.

You -> Axios -> Kitchen -> Axios -> Zod -> You

Without Zod, Axios can still deliver broccoli because delivery is not the same as validation.

The Missing Piece I Noticed

The better system has Zod in two places, not one.

Zod protects both directions: input before the request is sent and output after the response comes back.
You
  -> Zod checks input
  -> Axios sends request
  -> Backend
  -> Axios receives response
  -> Zod checks response
  -> You

That means bad user input can be stopped before Axios sends it, and bad backend data can be stopped before the UI uses it.

Real Code Mapping

Input validation comes first:

const inputSchema = z.object({
  token: z.string()
})

const validInput = inputSchema.safeParse(body)

if (!validInput.success) {
  throw new Error("Invalid input")
}

Then Axios sends validated data:

await axios.post('/api/auth/google', validInput.data)

Then response validation happens after Axios returns:

const responseSchema = z.object({
  accessToken: z.string(),
  user: z.object({
    name: z.string()
  })
})

const validResponse = responseSchema.safeParse(res.data)

if (!validResponse.success) {
  throw new Error("Invalid response")
}

Security and Stability Insight

Axios also matters because it centralizes how requests are made.

  • It can attach authorization headers and tokens consistently.
  • It can control timeouts, headers, and base URLs.
  • It can keep API calls organized instead of scattering fetch logic everywhere.
Authorization: Bearer token

But if Axios is misused, the risks show up quickly: wrong endpoints, missing headers, weak error handling, and bad data moving into the UI unchecked.

My Axios Mental Model

Axios = delivery
Zod = security guard
Backend = kitchen
Frontend = user

Axios is reliable transport. Zod is what makes the transport safe to use.

My rule now is simple:

Never trust data just because Axios delivered it. Always validate before using it.

Example: Google Login vs Staging and Production

This is the kind of example that makes the lesson real.

Imagine I am working on feature/google-auth and my goal is to add Google Login and Signup.

My target branch is staging, but staging and production still only support email and password authentication.

git fetch origin
git rebase origin/staging

Now my feature is being replayed on top of current staging reality.

Where the Problem Appears

My feature expects this:

POST /auth/login/google
{
  token: string
}

But staging only supports this:

POST /auth/login
{
  email: string
  password: string
}

This is the dangerous part: Git might not show any file conflict at all.

My frontend can call /auth/login/google successfully in my head while the backend in staging does not support it in reality.

That means the break is logical, not textual. Git cannot always see it.

Conflict Resolution Thinking

The first real engineering question is not "How do I keep my code?"

It is this:

Is the backend already deployed for this feature?

If the backend already exists, the task is to keep the feature and make sure the request shape still matches the schema.

If the backend is not ready yet, I must not blindly keep the integration just because rebase succeeded.

Proper Resolution Options

When backend is not ready, the safe choices are structural.

  • Feature flag the Google login UI until backend support is live.
  • Add fallback behavior that returns users to email login safely.
  • Hide the integration temporarily while keeping the code isolated.
if (featureFlags.googleAuthEnabled) {
  showGoogleLogin()
}
if (!googleAuthAvailable) {
  // fallback to email login
}

The goal is not to preserve every line I wrote. The goal is to preserve system stability.

Validation Is Where Truth Hits

pnpm build
pnpm test

This is where the hidden mismatch becomes visible.

Maybe my schema expects googleToken, but staging still returns accessToken.

// My feature expects
googleToken: string

// Staging response still returns
{
  accessToken: string
}

That build failure is good news. It means the system caught the drift before users did.

Other failures can be runtime crashes, missing Google auth dependencies, or incorrect environment configuration.

Hidden Security and Stability Risks

  • An exposed auth route can invite probing against an endpoint that is not actually ready.
  • Weak Google token validation can create authentication bypass risk.
  • Bad debugging habits can leak secrets, especially around auth environment variables.
console.log(process.env.GOOGLE_CLIENT_SECRET)

If something like that survives cleanup, the issue is no longer just buggy. It becomes critical.

Commit Hygiene for This Feature

  • Remove debug logs.
  • Remove mock tokens and hardcoded credentials.
  • Validate environment variable usage carefully.
  • Make sure the existing email login flow still works.

If I open the PR, the feature should be presented honestly as gated work with backend dependency risk.

[FE] Add Google Login (feature-gated)

The Real Insight

The most dangerous bugs are not merge conflicts. They are contract mismatches that Git cannot see.

That gives me a much better checklist when rebasing a feature like Google Login:

  • Does backend support it yet?
  • Does the schema still match?
  • Can it break the existing login flow?
  • Should it be behind a feature flag?

Key Terms I Understand Differently Now

Rebase Replay history on top of new truth.
Conflict Competing system realities that need reconciliation.
Validation Integrity check after structural change.
PR Review space, not the place where debugging should begin.
Staging The integration battlefield where assumptions meet reality.
Production The truth users actually experience.

My Rule After Today

If conflict surprises me in PR, I failed earlier.

That single sentence changes how I use Cursor too.

My prompts should always reinforce rebase, conflict explanation, validation, API contract awareness, type safety, backward compatibility, and no blind overwrite behavior.

Final Reflection

Today was the first time I understood that Git is not just version control.

Git is risk control.

And Cursor is not just helping me code. It is helping enforce engineering discipline that I do not naturally have yet.

The next step is obvious now: move into real failure simulation, where schema drift breaks the frontend and safety checks catch it before release.
